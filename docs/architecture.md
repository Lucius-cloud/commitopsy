# Architecture notes

## First vertical slice

The first slice accepts signed GitHub webhook events and stores a canonical, minimal representation in PostgreSQL.

### Trust boundary

The webhook signature is verified against the exact raw request body before JSON parsing. Requests without a valid `X-Hub-Signature-256` signature are rejected. The secret is loaded from environment configuration and is never returned by an API route.

### Idempotency

GitHub supplies `X-GitHub-Delivery`. The handler validates its UUID form and the repository persists it under a unique index. The persistence operation uses `ON CONFLICT DO NOTHING`; duplicate deliveries do not update the original row. The API acknowledges valid duplicate deliveries with `duplicate: true`.

### Event vs ingestion time

`occurred_at` stores a source-side event timestamp only where its semantics are defensible. A push payload does not provide a reliable push-delivery timestamp, so `occurred_at` remains `NULL` and the commit timestamp is retained separately. `received_at` is generated by PostgreSQL. Missing event time is not silently substituted with ingestion time.

### Data minimization

The code normalizes a limited subset of fields rather than retaining the full raw webhook body. Workflow path changes, commit/run references and a small number of descriptive fields are sufficient for the next correlation milestone.

### Next design decision

When the health monitor and 15-minute rule are implemented, define late-event policy explicitly. In particular, specify whether an incoming event can revise an incident after the rule's initial evaluation, how duplicate health failures are grouped into state transitions, and how incidents are deduplicated under concurrent processing.
